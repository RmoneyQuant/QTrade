One Binary, Two Modes

The strategy, the decoder, the order book, the cache and the execution engine are the same compiled code in backtesting and in production. Only two thin edges swap: where bytes come from, and where orders go.

The whole system

Read it top to bottom. Market data descends from the source edge through the shared core; order commands descend from the strategy to the venue edge; execution reports climb back up into the execution engine. Everything inside the indigo band is compiled once and never recompiled to go live.

What actually swaps

Strip the detail away and the claim becomes checkable. Two adapters at the top, two at the bottom, one core in the middle that does not know or care which mode it is running in. If a component needs an if backtest branch inside it, it belongs at an edge, not in the core.

What keeps them identical

Sharing the code is necessary but not sufficient — shared code can still behave differently if it can reach ambient state. These are the constraints that actually enforce parity.

Injected time

The strategy cannot read a clock

No system clock, no random(), no direct logging or file I/O. Everything arrives through injected handles. In backtest the SimClock is advanced by event timestamps; in live the LiveClock free-runs. Same call site, same code.

Byte-level replay

Record raw packets, not parsed events

Journal the undecoded multicast payload in live. The backtest then replays literally the same bytes through literally the same decoder, so decoder bugs reproduce instead of hiding.

Capture order

Do not sort by exchange timestamp

Contracts are spread across streams with independent sequence numbers, and live cannot reorder across them. Replaying in capture order preserves the interleaving the strategy will really see.

Modelled latency

Orders arrive later than they are decided

The simulator must insert the order at its simulated arrival time, competing with everything that arrived in between. Without this the backtest is a fantasy.

Single thread

The core is deterministic

One thread from decode to order emission, fed by a ring buffer. Parallelise across runs — parameter sweeps, separate days — never within one.

Explicit staleness

The strategy is told when the book is wrong

After a gap and before recovery completes the book is not trustworthy. UNINIT / RECOVERING / OK / STALE is visible state, so the strategy can stand down instead of trading noise.

Why the simulator cannot fill you at T

This is the single largest source of backtest results that do not survive contact with production. Between the moment the exchange stamps an event and the moment your order reaches the matching engine, other participants have already acted.

Queue position without a second order book

Your earlier question — who builds the LOB — resolves here. The book is built once in the core. The simulator adds only a small per-order overlay, so it never duplicates the book and never disagrees with what the strategy saw.

Because MTBT is order-by-order, you know the exact identity of every order ahead of yours. That means cancellations ahead of you can be tracked precisely, which is the part depth-based backtests can only estimate.

Proving parity, not assuming it

Sharing code makes divergence unlikely, not impossible. The journal closes the loop: because live records raw packets alongside every command and report, a production session can be re-run through the backtester and the two decision streams compared directly.
