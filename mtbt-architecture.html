Multi-exchange backtest & live engine

One Binary, Two Modes

One exchange-agnostic core, compiled once, running unchanged in backtest and in production. Exchanges plug in at the top through per-venue decoders; the venue plugs in at the bottom. Nothing in the core knows which exchange or which mode it is running.

Three layers, not two

The earlier draft pushed raw packets into a decoder inside the core. That only works for one protocol. With NSE, MCX and CME the decoder has to move out to the exchange edge, which splits the system into three layers rather than two.

Transport differs per exchange and per mode — a UDP receiver or a file reader. Decoder and normaliser differ per exchange but are shared across modes, and this is where the parity guarantee actually lives: the NSE decoder is one piece of code driving both the live path and the replay path. The core is common to everything and sees only internal event types.

The adapter that keeps modes honest

Zoom into one exchange. The transports differ — a socket versus a file — but they converge immediately, and everything downstream of that convergence is one piece of code. That single decoder is where backtest/live parity is actually enforced, because a decoder bug reproduces identically on both paths instead of hiding on one.

Time is a scheduler, not a counter

A clock advanced only by market data cannot detect the absence of market data — and that absence is exactly what a staleness timeout or a missed heartbeat is. If the feed goes silent for five seconds, a data-driven clock jumps five seconds instantly and never fires the timer that should have marked the book stale.

The correct model is a discrete-event scheduler holding a priority queue. Market data is one source among several. Pop the earliest event, set the clock to its timestamp, dispatch it; the handler may enqueue more events. Live uses the same interface with real timers.

The internal event vocabulary

This is where exchange-agnostic designs usually fail. The tempting move is to define internal events as the union of everything all three exchanges publish, which produces a wide struct full of optional fields — and then the core starts branching on which fields are populated, and exchange-specificity is back, just hidden.

Define events by what the core must do instead. If a decoder cannot express something in that vocabulary, the vocabulary is wrong; widening the struct is not the fix.

// the core needs to maintain a book, track trades, know session state OrderAdd { instrument, order_id, side, price_ticks, qty, ts } OrderModify { instrument, order_id, price_ticks, qty, ts } OrderCancel { instrument, order_id, ts } Trade { instrument, buy_id, sell_id, price_ticks, qty, ts } TradeCancel { instrument, buy_id, sell_id, price_ticks, qty, ts } SessionPhase{ scope, phase, ts } BookReset { instrument, reason, ts } // gap, recovery, DR switchover // NOT this — the union trap: // MarketEvent { order_id: Option<u64>, level_idx: Option<u8>, ... }

The harder problem is that these two families are not interchangeable. NSE MTBT is order-by-order, so every resting order has an identity and exact queue position is computable. Many feeds publish only aggregated depth, where it simply is not. Flatten them into one book type and a strategy relying on queue position will work on NSE and quietly degrade to guesswork elsewhere.

The simulated exchange sees nothing of yours

The venue is not part of your process. In production NSE has its own book and your code cannot look inside it, so if the simulator reads your cache you have built a coupling that does not exist in production — which is precisely the sort of thing that makes a backtest lie.

There is a sharper argument too. Your feed-derived book can go STALE after a packet gap. A real exchange does not become uncertain because your receiver dropped packets. A simulator reading your cache inherits your corruption and starts filling you against a book that never existed. Independence removes that whole failure class, and makes the simulator unit-testable against synthetic order flow with no core dependency at all.

Still open

How many book instances does the core create?

One shared, one per strategy, or one per group — deliberately undecided. The design keeps the choice open by making the book a pure function of the event stream with no other dependencies, so instance count is a startup wiring decision rather than a structural one. Benchmark it on a real day of FO capture before committing: build books for your realistic subscription set on one core, measure the fraction of a core it costs, multiply by strategy count. If it fits, per-strategy isolation is nearly free and worth having.

Why the simulator cannot fill you at T

Between the moment the exchange stamps an event and the moment your order reaches the matching engine, other participants have already acted. This is the largest single source of backtest results that do not survive production.

One asymmetry to be careful about: recorded MTBT lets you estimate feed latency, though the difference between exchange and capture timestamps includes clock offset unless you are PTP-synced, so trust the distribution shape rather than the absolute mean. Outbound latency — decide to matching engine — is not observable from market data at all. Until you have real order round-trips it is an assumption, so model it pessimistically.

What keeps the modes identical

Shared code is necessary but not sufficient — shared code still diverges if it can reach ambient state. These constraints are what actually enforce parity, and they are cheapest to adopt before the first strategy exists.

Injected time

Nothing in the core reads a clock

No system clock, no random(), no direct logging or file I/O. Time arrives only from the scheduler. This one rule prevents most divergence, and it is enforceable by simply not exposing the alternatives.

Total ordering

Every tie has a defined winner

Events sharing a nanosecond are ordered by (timestamp, class, seq) with the sequence assigned at enqueue. Without this the same backtest run twice gives different answers, which is a correctness bug wearing a performance costume.

Shared decoder

One decoder per exchange, both paths

Live and replay converge before decoding, so a decoder bug reproduces in backtest instead of waiting for production. Record raw packets per exchange to keep that property available.

Capture order

Do not sort by exchange timestamp

Instruments are spread across streams with independent sequence numbers, and live cannot reorder across them. Replaying in capture order preserves the interleaving production will actually see.

Venue isolation

The simulator reads nothing of yours

Commands in, reports out, its own books. Identical interface to the live gateway, so the execution engine cannot tell them apart — and your feed gaps cannot corrupt it.

Explicit staleness

The strategy is told when the book is wrong

After a gap and before recovery completes the book is untrustworthy. UNINIT / RECOVERING / OK / STALE is visible state, so a strategy can stand down rather than trade noise.

Proving parity, not assuming it

Because live records raw packets per exchange alongside every command and report, a production session can be re-run through the backtester and the two decision streams compared directly. Any divergence means the strategy reached ambient state it should not have been able to touch.

Build order

Correctness and stability first, in an order where each stage validates the one before it. Performance work is deliberately absent — no core pinning, no NUMA placement, no kernel bypass. Those are live-path concerns and premature until the throughput budget is measured against something that already works.
